## Основная идея

> [!tip] Простыми словами: MVVM разделяет экран, данные и действия, чтобы приложение было проще понимать и менять.

Это уже основа почти всех практических билетов: интерфейс, команды, вычисления, анимация и БД.

> [!note]
> Дополнение из методички: C# рассматривается как основной язык для платформы .NET. Он является объектно-ориентированным языком со статической типизацией и поддерживает полиморфизм, свойства, делегаты, события, лямбда-выражения, исключения и обобщённые типы. Поэтому MVVM в Avalonia удобно объяснять через уже изученные элементы C#: классы, свойства, интерфейсы, делегаты, события и задачи `Task`.

## MVVM

> [!tip] Простыми словами: MVVM — это три роли: что показываем, какие данные храним и кто связывает одно с другим.

MVVM расшифровывается так:

- Model — данные и предметная логика;
- View — интерфейс;
- ViewModel — связующее звено между интерфейсом и логикой.

## Общая схема

> [!tip] Простыми словами: Пользователь нажимает на интерфейс, интерфейс обращается к ViewModel, а ViewModel уже работает с логикой и данными.

```text
Пользователь
    ↓
View
    ↓ Binding / Command
ViewModel
    ↓
Model / Service / Database
```

## View

> [!tip] Простыми словами: View — это внешний вид окна, без основной логики.

View — то, что видит пользователь.

В Avalonia это обычно файл:

```text
MainWindow.axaml
```

Пример:

```xml
<StackPanel>
    <TextBox Text="{Binding InputValue}" />
    <Button
        Content="Вычислить"
        Command="{Binding CalculateCommand}" />
    <TextBlock Text="{Binding Result}" />
</StackPanel>
```

Здесь описан только интерфейс:

- поле ввода;
- кнопка;
- поле результата.

В View не должно быть основной вычислительной логики и SQL-запросов.

Что говорить:

View отвечает за отображение интерфейса и взаимодействует с ViewModel через привязки и команды.

> [!note]
> Дополнение из методички: инкапсуляция означает объединение данных и действий над ними внутри класса, а также сокрытие деталей реализации. В MVVM это проявляется в том, что View не знает, как именно выполняются вычисления или запросы к базе данных. Она видит только открытый интерфейс ViewModel: свойства и команды.

## ViewModel

> [!tip] Простыми словами: ViewModel — это посредник: хранит данные для экрана и команды пользователя.

ViewModel хранит состояние интерфейса и действия пользователя.

```csharp
public class MainWindowViewModel
{
    public string InputValue { get; set; }
    public string Result { get; set; }
    public ICommand CalculateCommand { get; }

    public MainWindowViewModel()
    {
        CalculateCommand = new RelayCommand(Calculate);
    }

    private void Calculate()
    {
        Result = InputValue;
    }
}
```

Здесь:

`InputValue`

хранит введённое значение.

`Result`

хранит результат.

`CalculateCommand`

представляет действие кнопки.

`Calculate()`

выполняет операцию.

Что говорить:

ViewModel содержит свойства, к которым привязан интерфейс, и команды, вызываемые пользователем. Она не должна напрямую управлять кнопками и текстовыми полями.

> [!note]
> Дополнение из методички: свойство в C# — это элемент класса, который имитирует переменную, но фактически работает через аксессоры `get`, `set` или `init`. Поэтому свойства ViewModel подходят для Binding: внешне Avalonia обращается к ним как к обычным данным, а внутри сеттера можно добавить проверку, вычисление или уведомление интерфейса.

## Model

> [!tip] Простыми словами: Model — это данные предметной области без знаний об интерфейсе.

Model хранит данные предметной области.

Например, результат вычисления:

```csharp
public class CalculationResult
{
    public int Id { get; set; }
    public double InputValue { get; set; }
    public double ResultValue { get; set; }
    public DateTime CreatedAt { get; set; }
}
```

Этот класс описывает одну запись:

- идентификатор;
- исходное значение;
- результат;
- время вычисления.

Model обычно не знает ничего о кнопках, окнах и элементах интерфейса.

Что говорить:

Model описывает данные предметной области и при необходимости содержит относящуюся к ним логику.

> [!note]
> Дополнение из методички: класс в C# является универсальным комплексным типом данных, который содержит характеристики и поведение моделируемой сущности. В примере `CalculationResult` характеристики представлены свойствами `Id`, `InputValue`, `ResultValue` и `CreatedAt`.

## Service

> [!tip] Простыми словами: Service — отдельный помощник для вычислений или другой логики, чтобы не перегружать ViewModel.

Для вычислений или БД часто используют отдельные сервисы.

```csharp
public class CalculatorService
{
    public double Calculate(double value)
    {
        return value * value;
    }
}
```

ViewModel вызывает сервис:

```csharp
private readonly CalculatorService _calculatorService;

public MainWindowViewModel()
{
    _calculatorService = new CalculatorService();
}

private void Calculate()
{
    double value = double.Parse(InputValue);
    double result = _calculatorService.Calculate(value);
    Result = result.ToString();
}
```

Зачем отдельный сервис:

- ViewModel становится проще;
- вычисления можно менять отдельно;
- код не дублируется;
- сервис можно тестировать независимо.

> [!note]
> Дополнение из методички: это пример практического применения инкапсуляции. Детали вычисления скрыты внутри `CalculatorService`, а ViewModel использует открытый метод `Calculate`.

## DatabaseService

> [!tip] Простыми словами: DatabaseService прячет всю работу с базой за понятными методами.

Работу с базой лучше выносить отдельно:

```csharp
public class DatabaseService
{
    public async Task SaveResultAsync(CalculationResult result)
    {
        // Подключение к БД и INSERT
    }

    public async Task<List<CalculationResult>> LoadResultsAsync()
    {
        // SELECT из БД
        return new List<CalculationResult>();
    }
}
```

ViewModel только вызывает готовые методы:

```csharp
await _databaseService.SaveResultAsync(record);
```

Она не обязана знать все детали подключения и SQL.

Что говорить:

DatabaseService инкапсулирует работу с базой данных. Он открывает соединение, выполняет SQL-запросы и преобразует записи БД в объекты.

> [!note]
> Дополнение из методички: `List<T>` относится к коллекциям для работы со списками и представляет массив переменной длины. Поэтому `Task<List<CalculationResult>>` означает асинхронную операцию, которая после завершения возвращает список объектов `CalculationResult`.

> [!note]
> Дополнение из методички: `Task` представляет продолжительную задачу, выполняемую асинхронно в пуле потоков. Это объясняет, почему методы работы с базой часто имеют тип `Task` или `Task<T>`: операция может занимать время, а интерфейс не должен зависать во время ожидания результата.

## Data Binding

> [!tip] Простыми словами: Binding связывает элемент интерфейса со свойством по имени.

Data Binding — механизм связи свойства ViewModel с элементом интерфейса.

```xml
<TextBox Text="{Binding InputValue}" />
```

Значение TextBox связано со свойством:

```csharp
public string InputValue { get; set; }
```

Связь работает по имени.

Если написано:

```xml
<TextBlock Text="{Binding Result}" />
```

Avalonia ищет свойство Result в текущей ViewModel.

Простое объяснение:

Binding позволяет не искать элемент интерфейса вручную и не присваивать ему значение напрямую. Интерфейс связан со свойством ViewModel.

Если асинхронный метод меняет свойство `Result`, Binding тоже работает обычным образом: свойство изменилось, `OnPropertyChanged()` сообщил об этом, интерфейс перечитал значение.

Пример:

```csharp
Result = "Считаю...";
await Task.Delay(2000);
Result = "Готово";
```

> [!tip] Простыми словами: Binding не волнует, обычный метод поменял `Result` или асинхронный. Главное, чтобы ViewModel сообщила: “значение изменилось”.

## DataContext

> [!tip] Простыми словами: DataContext говорит интерфейсу, в каком объекте искать свойства и команды.

Чтобы View понимала, где искать InputValue, Result и CalculateCommand, ей назначают ViewModel.

Например:

```csharp
DataContext = new MainWindowViewModel();
```

DataContext — объект, внутри которого View ищет свойства и команды, указанные в привязках.

Цепочка:

```text
Text="{Binding Result}"
        ↓
View смотрит в DataContext
        ↓
DataContext содержит MainWindowViewModel
        ↓
Avalonia находит свойство Result
```

Что говорить:

DataContext задаёт объект, используемый как источник данных для привязок.

## Почему простого свойства недостаточно

> [!tip] Простыми словами: Чтобы экран обновился, мало изменить значение в памяти: нужно ещё сообщить об изменении.

Такое свойство:

```csharp
public string Result { get; set; }
```

изменится в памяти, но интерфейс может не узнать об изменении.

Для уведомления используется INotifyPropertyChanged.

```csharp
public class MainWindowViewModel : INotifyPropertyChanged
{
    public event PropertyChangedEventHandler? PropertyChanged;

    protected void OnPropertyChanged(
        [CallerMemberName] string? propertyName = null)
    {
        PropertyChanged?.Invoke(
            this,
            new PropertyChangedEventArgs(propertyName));
    }
}
```

Свойство:

```csharp
private string _result = string.Empty;

public string Result
{
    get => _result;
    set
    {
        _result = value;
        OnPropertyChanged();
    }
}
```

Когда значение меняется:

```csharp
Result = "Готово";
```

событие PropertyChanged сообщает интерфейсу:

Свойство Result изменилось, его нужно перечитать.

Без этого результат может измениться внутри ViewModel, но на экране останется старое значение.

> [!note]
> Дополнение из методички: событие в C# объявляется с помощью ключевого слова `event`, а вызов события выполняется через `Invoke`. В примере `PropertyChanged?.Invoke(...)` ViewModel уведомляет подписчиков, что свойство изменилось. В роли подписчика выступает механизм привязок Avalonia.

## Команда

> [!tip] Простыми словами: Команда — это объект-действие, который кнопка может вызвать через Binding.

Кнопка:

```xml
<Button Command="{Binding CalculateCommand}" />
```

привязана не к методу напрямую, а к объекту команды.

Во ViewModel:

```csharp
public ICommand CalculateCommand { get; }
```

В конструкторе:

```csharp
CalculateCommand = new RelayCommand(Calculate);
```

Для асинхронного метода команда может получить async-лямбду:

```csharp
CalculateCommand = new RelayCommand(async () => await CalculateAsync());
```

При нажатии кнопки происходит:

```text
Button
→ вызывает ICommand.Execute
→ RelayCommand запускает переданный метод
→ выполняется Calculate()
```

## RelayCommand

> [!tip] Простыми словами: RelayCommand хранит переданное действие и запускает его, когда команда выполняется.

Упрощённый вариант:

```csharp
public class RelayCommand : ICommand
{
    private readonly Action _execute;

    public RelayCommand(Action execute)
    {
        _execute = execute;
    }

    public bool CanExecute(object? parameter)
    {
        return true;
    }

    public void Execute(object? parameter)
    {
        _execute();
    }

    public event EventHandler? CanExecuteChanged;
}
```

Разбор:

```csharp
private readonly Action _execute;
```

Поле хранит действие.

```csharp
public RelayCommand(Action execute)
```

Конструктор получает метод или лямбду.

```csharp
public void Execute(object? parameter)
{
    _execute();
}
```

При выполнении команды вызывается сохранённое действие.

> [!note]
> Дополнение из методички: делегат — это особый тип данных, позволяющий хранить ссылки на методы. `Action` является стандартным делегатом .NET и представляет действие, которое ничего не возвращает. Поэтому поле `_execute` может хранить ссылку на метод `Calculate` или на лямбда-выражение.

> [!note]
> Дополнение из методички: лямбда-выражение использует оператор `=>`. Слева указываются параметры, справа — выражение или блок действий. Поэтому запись `() => Calculate()` означает функцию без параметров, которая вызывает метод `Calculate`.

Пример передачи лямбды в команду:

```csharp
CalculateCommand = new RelayCommand(() => Calculate());
```

В методичке также выделяются стандартные делегаты:

- `Action` — действие без возвращаемого значения;
- `Func` — функция с возвращаемым значением;
- `Predicate` — функция, которая принимает один параметр и возвращает `bool`.

Для `RelayCommand` чаще всего нужен именно `Action`, потому что команда выполняет действие, а не возвращает результат.

Если действие асинхронное, в команду часто передают async-лямбду:

```csharp
new RelayCommand(async () => await StartAsync())
```

> [!tip] Простыми словами: команда всё равно хранит “что сделать”, просто это действие умеет ждать через `await`.

## Асинхронность в MVVM

> [!tip] Простыми словами: Асинхронность нужна, чтобы приложение ждало долгую операцию, но окно при этом не превращалось в неподвижную картинку.

Асинхронность — это когда программа может ждать долгую операцию и при этом не «замораживать» интерфейс.

```csharp
private async Task CalculateAsync()
{
    Result = "Считаю...";
    await Task.Delay(2000);
    Result = "Готово";
}
```

Что здесь происходит:

- `async` разрешает использовать `await`;
- `Task` означает, что метод представляет асинхронную операцию;
- `await Task.Delay(2000)` ждёт 2 секунды;
- во время ожидания окно не зависает;
- после ожидания код продолжается.

Связь с Binding:

```text
Result = "Считаю..."
→ OnPropertyChanged()
→ TextBlock обновился
→ await ждёт
→ Result = "Готово"
→ OnPropertyChanged()
→ TextBlock обновился ещё раз
```

Важно: асинхронность не обязательно означает новый поток. Она означает, что программа не блокирует выполнение во время ожидания.

## Полный путь выполнения

> [!tip] Простыми словами: Этот раздел показывает всю цепочку от ввода пользователя до обновления результата на экране.

Допустим, пользователь вводит 5 и нажимает кнопку.

1. Пользователь вводит 5 в TextBox.
2. Binding записывает 5 в InputValue.
3. Пользователь нажимает Button.
4. Button вызывает CalculateCommand.
5. RelayCommand вызывает Calculate().
6. Calculate читает InputValue.
7. Выполняется вычисление.
8. Результат записывается в Result.
9. OnPropertyChanged сообщает View.
10. TextBlock обновляет текст.
11. При необходимости результат сохраняется в БД.

## Типичные файлы

> [!tip] Простыми словами: Это обычные роли файлов в Avalonia-проекте: где интерфейс, где логика, где данные и сервисы.

`App.axaml`

Общие ресурсы и настройки приложения.

`App.axaml.cs`

Запуск приложения и создание главного окна.

`MainWindow.axaml`

Разметка окна.

`MainWindow.axaml.cs`

Минимальный code-behind, обычно инициализация окна.

`MainWindowViewModel.cs`

Свойства, команды и логика взаимодействия.

`CalculationResult.cs`

Модель данных.

`RelayCommand.cs`

Реализация ICommand.

`DatabaseService.cs`

Работа с БД.

Если нужно показать таблицу результатов из PostgreSQL, обычно добавляются:

`ObservableCollection<CalculationRecord> Records`

Коллекция записей, к которой привязывается таблица.

`DataGrid`

Элемент интерфейса, который показывает строки из `Records`.

```xml
<DataGrid ItemsSource="{Binding Records}" />
```

> [!tip] Простыми словами: `DatabaseService` достал записи из PostgreSQL, ViewModel положила их в `Records`, а `DataGrid` показал их на экране.

## WPF и Avalonia

> [!tip] Простыми словами: Для экзамена главное: архитектура похожа, даже если фреймворк другой.

На экзамене:

В билете указан WPF, но на macOS используется Avalonia. Архитектурные принципы остаются аналогичными: XAML-разметка, Data Binding, DataContext, ICommand и MVVM.

Основные различия фреймворков сейчас не нужны. Для защиты важнее показать, что требуемая архитектура сохранена.

## Дополнения из методички

> [!tip] Простыми словами: Здесь теория C# привязана к практическому MVVM-проекту.

### Связь MVVM с ООП

> [!tip] Простыми словами: MVVM использует обычные идеи ООП: классы, свойства, интерфейсы, события и инкапсуляцию.

MVVM удобно объяснять через основные принципы ООП:

- классы описывают элементы системы: ViewModel, Model, Service, Command;
- свойства предоставляют доступ к данным;
- инкапсуляция отделяет интерфейс от вычислений и БД;
- интерфейс `ICommand` задаёт контракт команды;
- делегаты и лямбда-выражения позволяют передавать поведение в `RelayCommand`;
- события уведомляют подписчиков об изменениях.

### Делегаты, лямбда-выражения и команды

> [!tip] Простыми словами: Команда получает действие как делегат, а лямбда помогает записать это действие коротко.

В методичке делегат определяется как тип данных для хранения ссылок на методы. Для объявления собственного делегата используется ключевое слово `delegate`.

```csharp
public delegate double Fun(double x);
```

Переменной такого типа можно присвоить любой метод с подходящей сигнатурой: в данном примере метод должен принимать `double` и возвращать `double`.

В MVVM тот же принцип используется в более практичном виде: `RelayCommand` получает действие типа `Action` и вызывает его при выполнении команды.

```csharp
private readonly Action _execute;

public RelayCommand(Action execute)
{
    _execute = execute;
}
```

Лямбда-выражения позволяют не создавать отдельный именованный метод, если действие короткое:

```csharp
Action<int> act = (a) => Console.WriteLine($"a = {a}");
```

Для команды это выглядит так:

```csharp
CalculateCommand = new RelayCommand(() => Calculate());
```

### События и уведомления интерфейса

> [!tip] Простыми словами: События нужны, чтобы ViewModel могла сказать интерфейсу: данные изменились.

В методичке событие связывается с делегатом и ключевым словом `event`.

```csharp
public delegate void NotifyHandler(float percentage);
public static event NotifyHandler OnNotify;
```

На событие можно подписаться методом или лямбда-выражением:

```csharp
Calculator.OnNotify +=
    (percentage) => Console.WriteLine("Выполнено: {0}%", percentage);
```

Вызов события выполняется через `Invoke`:

```csharp
OnNotify?.Invoke((float)Math.Round(100.0 * i / aRows, 1));
```

В MVVM используется та же идея: ViewModel сообщает View, что данные изменились.

```csharp
PropertyChanged?.Invoke(
    this,
    new PropertyChangedEventArgs(propertyName));
```

### Task и асинхронные сервисы

> [!tip] Простыми словами: Task нужен для долгих операций, чтобы приложение не зависало.

Методичка объясняет `Task` как базовый класс библиотеки TPL. Он представляет продолжительную задачу, выполняемую асинхронно в пуле потоков.

```csharp
Task t1 = Task.Run(() => { /* Действия задачи... */ });
```

Если задача возвращает результат, используется `Task<T>`:

```csharp
Task<string> t3 = Task<string>.Factory.StartNew((n) => {
    return $"Задача №{n}";
}, 3);
```

В Avalonia-проекте это важно для операций БД:

```csharp
public async Task<List<CalculationResult>> LoadResultsAsync()
```

Такой метод означает: операция выполняется асинхронно и после завершения возвращает список результатов.

### Коллекции и результаты вычислений

> [!tip] Простыми словами: Коллекция — это удобное место для хранения нескольких результатов.

В методичке коллекции рассматриваются как удобный способ хранить наборы объектов. Для списка результатов подходит `List<T>`.

```csharp
public async Task<List<CalculationResult>> LoadResultsAsync()
{
    return new List<CalculationResult>();
}
```

Здесь `List<CalculationResult>` хранит несколько объектов модели `CalculationResult`.

## Ответ на экзамене

> [!tip] Простыми словами: Это готовая короткая формулировка, которую можно произнести на защите.

Приложение построено по паттерну MVVM. View описывает интерфейс в XAML. ViewModel содержит свойства состояния и команды. Model описывает данные, а работа с вычислениями и базой может быть вынесена в отдельные сервисы. View получает данные из ViewModel через Binding, а действия пользователя передаются через ICommand. Для обновления интерфейса ViewModel реализует INotifyPropertyChanged.

Дополненный ответ:

С точки зрения C# ViewModel является классом со свойствами и командами. Свойства используются механизмом Binding, а команды реализуются через интерфейс `ICommand`. `RelayCommand` хранит действие в делегате `Action`, поэтому в команду можно передать метод или лямбда-выражение. Для уведомления интерфейса применяется событие `PropertyChanged`. Работа с БД выносится в `DatabaseService`, часто выполняется асинхронно через `Task`, а результаты могут храниться в коллекции `List<CalculationResult>`.
