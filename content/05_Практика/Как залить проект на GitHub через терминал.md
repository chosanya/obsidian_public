## 1. Открыть терминал в папке проекта

> [!tip] Простыми словами: сначала нужно оказаться именно в папке проекта, а не где-то рядом.

Проверить, что открыта нужная папка:

```bash
pwd
ls
```

`pwd` показывает текущую папку.

`ls` показывает файлы и папки внутри неё.

Если в списке видны файлы проекта, например `.sln`, `.csproj`, `Program.cs`, `MainWindow.axaml`, значит терминал открыт правильно.

## 2. Инициализировать Git

> [!tip] Простыми словами: `git init` включает историю изменений в этой папке.

```bash
git init
```

После этого в папке появляется скрытая папка `.git`. В ней Git хранит локальную историю проекта.

## 3. Создать .gitignore

> [!tip] Простыми словами: `.gitignore` говорит Git, какие мусорные и служебные файлы не нужно отправлять на GitHub.

Для Rider / .NET:

```gitignore
.idea/
bin/
obj/
.DS_Store
.env
```

Что обычно не надо коммитить:

- `.idea/` — настройки Rider;
- `bin/` — собранные файлы программы;
- `obj/` — временные файлы сборки;
- `.DS_Store` — служебный файл macOS;
- `.env` — файл с секретами, паролями и токенами.

Если `.gitignore` создали после `git add .`, лучше проверить статус и убрать лишние файлы из индекса.

## 4. Подготовить файлы

> [!tip] Простыми словами: перед сохранением версии нужно выбрать, какие файлы попадут в коммит.

```bash
git add .
git status
```

`git add .` подготавливает все изменения в текущей папке.

`git status` показывает, какие файлы попадут в коммит.

Проверить, что `bin`, `obj`, `.idea` и другие служебные файлы не попали в коммит.

Если что-то лишнее всё-таки попало, сначала исправляют `.gitignore`, а потом убирают файл из подготовленных:

```bash
git restore --staged путь/к/файлу
```

## 5. Создать коммит

> [!tip] Простыми словами: коммит — это сохранённая точка в истории проекта.

```bash
git commit -m "Add project"
```

Коммит — сохранённая версия проекта в локальной истории Git.

Сообщение коммита должно коротко объяснять, что изменилось.

Примеры:

```bash
git commit -m "Add Avalonia calculator"
git commit -m "Add PostgreSQL database service"
git commit -m "Fix result saving"
```

## 6. Создать пустой репозиторий на GitHub

> [!tip] Простыми словами: локальный проект уже есть на компьютере, теперь нужно создать пустое место для него на GitHub.

На GitHub создать новый репозиторий без README, `.gitignore` и лицензии.

Это важно: если GitHub сам создаст README или `.gitignore`, в удалённом репозитории уже будет первый коммит, и при отправке может появиться конфликт историй.

Скопировать HTTPS-ссылку:

```text
https://github.com/ЛОГИН/НАЗВАНИЕ.git
```

## 7. Подключить GitHub-репозиторий

> [!tip] Простыми словами: `remote` — это адрес GitHub-репозитория, куда потом отправятся коммиты.

```bash
git remote add origin https://github.com/ЛОГИН/НАЗВАНИЕ.git
```

Проверить:

```bash
git remote -v
```

Обычно `origin` — имя удалённого репозитория по умолчанию.

Если адрес ошибочный, его можно заменить:

```bash
git remote set-url origin https://github.com/ЛОГИН/НАЗВАНИЕ.git
```

## 8. Отправить проект

> [!tip] Простыми словами: `push` отправляет локальные коммиты на GitHub.

```bash
git branch -M main
git push -u origin main
```

`git branch -M main` переименовывает текущую ветку в `main`.

`git push -u origin main` отправляет ветку `main` на GitHub и запоминает связь с удалённой веткой.

Если GitHub просит обычный пароль, он не подойдёт. Нужно войти через GitHub CLI или использовать токен.

Авторизация через GitHub CLI:

```bash
gh auth login
```

Выбрать:

```text
GitHub.com
HTTPS
Login with a web browser
```

После входа:

```bash
gh auth setup-git
git push -u origin main
```

## Как отправлять следующие изменения

> [!tip] Простыми словами: дальше каждый раз один и тот же цикл: подготовить, сохранить, отправить.

После редактирования проекта:

```bash
git add .
git commit -m "Описание изменений"
git push
```

Перед коммитом полезно смотреть:

```bash
git status
```

А если нужно увидеть сами изменения:

```bash
git diff
```

## Что делают команды

```text
git add     — подготавливает изменения
git commit  — сохраняет их локально
git push    — отправляет коммиты на GitHub
git status  — показывает состояние файлов
```

Дополнительно:

```text
git init             — включает Git в папке проекта
git remote -v        — показывает подключённые GitHub-адреса
git branch -M main   — задаёт имя основной ветки
gh auth login        — вход в GitHub через GitHub CLI
gh auth setup-git    — настраивает Git для авторизации через gh
```

## Частые проблемы

### В коммит попали bin, obj или .idea

Проверить `.gitignore`, затем убрать лишнее из подготовленных файлов:

```bash
git restore --staged путь/к/файлу
```

Если файл уже попал в старый коммит, для учебного проекта обычно проще исправить это в следующем коммите.

### GitHub не принимает пароль

Обычный пароль от GitHub для `git push` не используется. Нужно авторизоваться через GitHub CLI:

```bash
gh auth login
gh auth setup-git
```

или использовать Personal Access Token.

### Ошибка remote origin already exists

Это значит, что `origin` уже добавлен.

Проверить:

```bash
git remote -v
```

Заменить адрес:

```bash
git remote set-url origin https://github.com/ЛОГИН/НАЗВАНИЕ.git
```

### На GitHub уже есть README

Если репозиторий создали не пустым, истории локального и удалённого репозитория могут отличаться.

Для экзаменационных проектов проще создать пустой репозиторий без README, `.gitignore` и лицензии.

## Коротко для экзамена или защиты

Чтобы залить проект на GitHub, нужно открыть терминал в папке проекта, выполнить `git init`, создать `.gitignore`, добавить файлы через `git add .`, создать коммит через `git commit -m "Add project"`, создать пустой репозиторий на GitHub, подключить его командой `git remote add origin ...` и отправить проект через `git push -u origin main`. Для следующих изменений используется цикл `git add .`, `git commit`, `git push`.
