# Проблемные места OOP1

## Класс `Complex` находится в `Program.cs`

Это допустимо для учебного примера, но для реального проекта класс лучше вынести в отдельный файл `Complex.cs`.

Что может спросить преподаватель:

- почему класс лежит в `Program.cs`;
- как лучше организовать проект.

## Активный код почти ничего не делает

Весь демонстрационный код закомментирован. При запуске выполняется только:

```csharp
Console.WriteLine();
```

Это не ошибка для лекционного примера, но на защите нужно объяснить, что основной смысл проекта в классе и тестах.

## Индексатор не проверяет `null`

В индексаторе вызывается:

```csharp
part.ToLower()
```

Если передать `null`, будет исключение.

## Унарный минус меняет только мнимую часть

В коде:

```csharp
public static Complex operator -(Complex z1)
{
    return new Complex(z1.Re, -z1.Im);
}
```

С математической точки зрения унарный минус для комплексного числа обычно должен менять знак обеих частей: `-a - bi`.

Здесь это потенциально спорное место. Код не исправляется автоматически, но его нужно уметь объяснить.

## Оператор `==` не проверяет `null`

В коде:

```csharp
public static bool operator ==(Complex z1, Complex z2)
{
    return z1.Re == z2.Re && z1.Im == z2.Im;
}
```

Если один из операндов будет `null`, возможна ошибка. В текущих тестах такие случаи не проверяются.

## Сравнение `double` через `==`

В `Equals` и `operator ==` значения `double` сравниваются напрямую. Для учебного примера это нормально, но в вычислительной математике часто используют сравнение с погрешностью.

## Не все возможности покрыты тестами

Тесты проверяют:

- конструктор;
- `operator +`;
- `operator ==`;
- `ToString`.

Не проверяются:

- индексатор;
- `Abs`;
- `operator -`;
- явное и неявное преобразование типов;
- `Equals` для `double` и `int`;
- поведение с `null`.
