# Проблемные места SmakLivery

## SQL-запросы

### `CREATE TYPE`

Факт из кода:

`DbHelper.CreateDbAsync()` создает PostgreSQL enum `order_status`, если такого типа еще нет.

Пояснение:

Это нужно для хранения статуса заказа в БД как отдельного enum-типа.

Что требует ручной проверки:

- Значения PostgreSQL enum: `accepted`, `preparing`, `out_for_delivery`, `delivered`, `cancelled`.
- Соответствие этих значений C# enum `OrderStatus` после `MapEnum<OrderStatus>("order_status")`.

## Создание таблицы `order`

Факт из кода:

Таблица `"order"` создается с полями `id`, `address`, `status`, `courier_id`.

Пояснение:

Имя `order` взято в кавычки, потому что это ключевое слово SQL.

Что требует ручной проверки:

- Для `courier_id` нет явного `FOREIGN KEY` на `courier(id)`.
- Если связь должна быть обязательной, сейчас `courier_id` допускает `NULL`.

## Создание таблицы `courier`

Факт из кода:

В SQL есть фрагмент:

```sql
FOREIGN KEY (id)
```

Пояснение:

Внешний ключ должен указывать, на какую таблицу и поле он ссылается, например `FOREIGN KEY (...) REFERENCES ...(...)`. В текущем виде это выглядит как незавершенная или ошибочная часть схемы.

Что требует ручной проверки:

- Выполняется ли этот SQL в PostgreSQL без ошибки.
- Какая связь реально планировалась: `order.courier_id -> courier.id`.
- Почему в имени поля `firtsname` опечатка, а не `firstname`.

## Связь `order` / `courier`

Факт из кода:

Загрузка заказов выполняется запросом:

```sql
SELECT * FROM "order" JOIN courier ON courier.id = "order".courier_id ORDER BY "order".id;
```

Пояснение:

Это обычный `JOIN`, то есть `INNER JOIN`. Он возвращает только те заказы, у которых есть подходящий курьер.

Что требует ручной проверки:

- Заказы без курьера не попадут в список.
- Для отображения всех заказов, включая заказы без курьера, обычно нужен `LEFT JOIN`.
- В коде чтение колонок идет по индексам, а `SELECT *` при `JOIN` делает порядок колонок менее очевидным.

## `INSERT`

Факт из кода:

`AddOrderAsync()` добавляет только `address` и `status`:

```sql
INSERT INTO "order" (address,status) VALUES (@Address,@Status) RETURNING Id;
```

Пояснение:

`courier_id` при создании заказа не записывается, даже если в форме есть поле `CourierId`.

Что требует ручной проверки:

- Нужно ли сохранять `CourierId` при добавлении заказа.
- Что произойдет со списком после добавления заказа без курьера при текущем `INNER JOIN`.

## `UPDATE`

Факт из кода:

`EditOrderAsync()` собирает часть SQL-строки динамически:

```csharp
var cid = (order.CourierId is not null) ? ", courier_id = @CourierId" : "";
```

Пояснение:

Параметры используются безопасно, но сама структура SQL меняется строковой склейкой.

Что требует ручной проверки:

- Если `CourierId == null`, существующий `courier_id` не очищается в БД.
- Нужно ли уметь снять курьера с заказа.

## `DELETE`

Факт из кода:

Удаление выполняется через параметр:

```sql
DELETE FROM "order" WHERE Id=@Id;
```

Пояснение:

Использование параметра защищает от SQL-инъекции для значения `Id`.

Что требует ручной проверки:

- Регистр имени колонки в PostgreSQL обычно не важен без кавычек, но в проекте в других местах используется `id`.
- Нужно ли подтверждение удаления в UI.

## Безопасность SQL-параметров

Факт из кода:

Для пользовательских значений используются параметры: `@Address`, `@Status`, `@CourierId`, `@Id`.

Пояснение:

Это правильно: значения не вставляются напрямую в SQL-строку.

Что требует ручной проверки:

- Строка подключения с логином и паролем захардкожена в коде.
- Динамическая склейка `UPDATE` сейчас не вставляет пользовательское значение напрямую, но усложняет сопровождение.

## `async void`

Факты из кода:

- `App.OnStartup` объявлен как `async void`.
- `MainWindow.Window_Loaded` объявлен как `async void`.
- `RelayCommand` принимает `Action<object?>`, поэтому асинхронные лямбды в командах фактически превращаются в `async void`.

Пояснение:

Для обработчиков событий WPF `async void` допустим, но в командах и обычной логике лучше возвращать `Task`, чтобы можно было отлавливать ошибки.

Что требует ручной проверки:

- Ошибки внутри асинхронных команд могут быть обработаны неявно или неудобно.
- `Save_Click` вызывает `SaveCommand.Execute(null)` и сразу закрывает окно, не дожидаясь завершения сохранения как `Task`.

## Пустые или скрытые `catch`

Факт из кода:

В `MainViewModel.LoadOrdersAsync()` есть:

```csharp
catch { }
```

Пояснение:

Ошибка загрузки заказов полностью скрывается.

Что требует ручной проверки:

- Если SQL-запрос упадет, список просто останется пустым.
- Пользователь не узнает причину ошибки.
- Для учебного проекта полезно хотя бы вывести `MessageBox` или лог.

## `lock` и async/await

Факт из кода:

`lock` в проекте не используется.

Пояснение:

Это нормально: проект не запускает несколько потоков для общей памяти. Основная асинхронность связана с ожиданием БД, а не с ручной синхронизацией потоков.

Что требует ручной проверки:

- Не нужно добавлять `lock` для текущего сценария.
- Важнее корректно обрабатывать ошибки асинхронных операций.

## Возможные ошибки Data Binding

Факты из кода:

- `SelectedOrder` — auto-property без вызова `OnPropertyChanged`.
- `Order` не реализует `INotifyPropertyChanged`.
- В `AddOrEditWindow` `DataContext` окна — `AddEditViewModel`, а `Form.DataContext` — `viewModel.Order`.
- `SaveButtonText` находится в `AddEditViewModel`, а поля формы находятся в `Order`.

Пояснение:

Разные `DataContext` внутри окна могут быть рабочими, но это важно понимать при поиске ошибок Binding.

Что требует ручной проверки:

- Кнопка `Content="{Binding SaveButtonText}"` находится вне `Form`, поэтому она берет свойство из `AddEditViewModel`.
- Поля `Id`, `Address`, `Status`, `CourierId` находятся внутри `Form`, поэтому они берут свойства из `Order`.
- Команда удаления может быть недоступна из-за проверки типа в `CanExecute`.

## Соответствие MVVM

Факты из кода:

- Данные и команды вынесены в ViewModel.
- `MainWindow` устанавливает `DataContext`.
- `AddOrEditWindow` содержит обработчики `Save_Click` и `Cancel_Click`.

Пояснение:

Проект демонстрирует MVVM, но не полностью отделяет View от логики действий.

Что требует ручной проверки:

- В идеальном MVVM кнопки формы можно было бы привязать к `SaveCommand` и `CancelCommand` напрямую.
- `CancelCommand` сейчас ничего не делает.
- `ResultOk` хранится в окне, а не во ViewModel.
